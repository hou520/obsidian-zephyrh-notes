Python 里处理循环依赖时常用的类型注解专用 import 写法。

## 这段代码在做什么

from typing import TYPE_CHECKING, Optional

if TYPE_CHECKING:

from app.services.quality_inspection.qt_tag_match_handlers import HandlerResult

- `TYPE_CHECKING` 来自 `typing`
- 运行时它是 `False`，所以 `if` 里的 import 不会执行
- 静态类型检查（Pylance、mypy、pyright）分析代码时，会把它当作 `True`，因此类型检查器能识别 `HandlerResult` 这个类型

也就是说：这段 import 只给 IDE/类型检查用，不参与实际运行。

## 为什么要这么写

因为 `qt_tag_match.py` 和 `qt_tag_match_handlers.py` 互相依赖，形成了循环 import：

qt_tag_match.py

└── 需要 HandlerResult（合并 handler 结果、组装 debug_info）

qt_tag_match_handlers.py

└── 需要 PromptProfile、build_qt_tag_match_prompt_variables、validate_matched_tags 等（来自 qt_tag_match.py）

如果在 `qt_tag_match.py` 顶部直接写：

from app.services.quality_inspection.qt_tag_match_handlers import HandlerResult

加载顺序会变成：

1. 开始加载 `qt_tag_match.py`
2. 还没加载完，就去加载 `qt_tag_match_handlers.py`
3. `handlers` 又去 import `qt_tag_match.py`
4. 此时 `qt_tag_match` 尚未初始化完成 → 容易 `ImportError` / 拿到不完整的模块

所以不能把 `HandlerResult` 放在文件顶部的运行时 import。

## 实际采用的组合策略

这个文件用了两层手段：

|手段|位置|作用|
|---|---|---|
|`TYPE_CHECKING` import|第 8–9 行|让类型检查器认识 `HandlerResult`，运行时不 import|
|字符串注解 `"HandlerResult"`|如 `_build_debug_info(merged: "HandlerResult")`|延迟解析类型，避免运行时立刻需要该类|
|函数内局部 import|如 `merge_handler_results` 第 150 行、`qt_tag_match_v2` 第 585 行|真正运行时再 import，此时两个模块都已加载完成|

例如：

qt_tag_match.pyLines 149-150

from app.services.quality_inspection.qt_tag_match_handlers import HandlerResult

函数被调用时，两个模块通常都已初始化，局部 import 就安全了。

## 一句话总结

第 8–10 行的含义是：在类型注解里使用 `HandlerResult`，但避免在模块加载阶段触发循环 import。  
这是 Task 5 拆分 v1/v2 并引入 `handlers` 模块后的常见写法，本身没有问题。若以后要彻底消除循环依赖，可以把 `HandlerResult` 抽到第三个独立模块（如 `qt_tag_match_types.py`），两边都从那里 import。
